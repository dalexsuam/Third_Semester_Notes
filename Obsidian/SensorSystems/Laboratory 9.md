# <span style="color:rgb(223, 109, 109)">Serial Peripheral Interface (SPI)</span> 

SPI, or Serial Peripheral Interface, is the new communication protocol that we will use to control the LED matrix on the board. You have probably noticed that this matrix sometimes turns on by itself even when you are not using it, but today we will learn how to properly program it.

SPI is a **synchronous serial communication protocol**, which means two things. First, it is serial: the data is transmitted one bit after another, rather than in parallel across many lines. Second, it is synchronous: in contrast to protocols like UART, the devices involved share a common clock line. The microcontroller, which always acts as the master in the communication, provides this clock, and the peripheral, which acts as the slave, uses this clock to know exactly when to read or write each bit.

One important point is that SPI is typically used only for **short-distance communication**. The reason is simple: while I²C needs only two wires to connect multiple devices, SPI requires several dedicated lines. In addition to the shared clock, **SPI needs one line for data going from the master to the slave, another line for data going from the slave back to the master, and a separate line for selecting the slave you want to talk to.** When you have many devices or longer cables, this number of wires becomes impractical, ==which is why SPI is mostly used for short, point-to-point connections on the same board.==
Despite requiring more wires, SPI offers an advantage that is essential for devices like LED matrices: it is **fast**. Because the communication is synchronized by the clock generated by the master, and because the protocol itself is very simple, SPI can operate at much higher speeds than I²C. This is why it is the preferred protocol whenever large amounts of data need to be transferred quickly and reliably, such as when updating a display.

In summary, SPI is a simple but very efficient synchronous serial protocol used for short-range, high-speed communication. It relies on a shared clock, uses separate data lines for sending and receiving, and communicates one bit at a time. We will use SPI to program the LED matrix because this protocol provides the speed and timing precision required to update the display correctly.
![[Pasted image 20251124081023.png]]

SPI (Serial Peripheral Interface) operates using a **single master device**—typically a microcontroller—and one or more **slave devices**, such as sensors or displays. Unlike I²C, which allows multi-master configurations, SPI is strictly **single-master**, though it can support **multiple slaves**.

The master and the slaves are connected through several dedicated lines:
- **SCLK (Serial Clock):**  
    Generated by the master and sent to the slave. This line ensures synchronous communication, meaning data transfers are coordinated with the clock signal.
- **MOSI (Master Out, Slave In):**  
    This line carries data transmitted **from the master to the slave**.
- **MISO (Master In, Slave Out):**  
    This line carries data **from the slave back to the master**.
    
Because MOSI and MISO are separate, SPI supports **full-duplex communication**, allowing data to be sent and received simultaneously.

- **SS / CS (Slave Select or Chip Select):**  
    This line is used by the master to choose which slave device is active. When the master pulls a slave’s SS line **low**, that slave becomes enabled and listens to the communication.  
    With only one slave, this is simple. With multiple slaves, each slave requires **its own dedicated SS line**, which is one reason SPI is more practical for short-distance communication on a single board.
### <span style="color:rgb(161, 40, 226)">How SPI Communication Actually Works</span>


![[Pasted image 20251124081322.png]]

SPI communication relies on the master and slave behaving like **shift registers**. Each device has a register containing the bits it wants to send—typically 8 bits in simple configurations. During transmission, the master shifts out its data **bit by bit** through the MOSI line. At every clock pulse, **one bit exits the master’s register** (usually starting with the **most significant bit**) and moves to the slave’s input register.

The slave receives these bits sequentially, shifting them into its own register in sync with the clock. At the same time, the slave can also shift data out on the MISO line so the master receives a bit back during the same clock cycle. This makes SPI capable of **full-duplex** operation: both devices can send and receive simultaneously.

Depending on the application, the master may use the returned bits (for example, reading a sensor), or it may simply ignore them. In some cases, the received bits are forwarded (shifted out) to other chained devices, which is another feature SPI enables.

In short, during every clock cycle:

- one bit moves from master → slave on MOSI
- one bit can move from slave → master on MISO
- both shift registers move one position
    
And the data is typically transmitted **MSB first**.

### <span style="color:rgb(161, 40, 226)">SPI Wiring: Why It’s <i>Not Always</i> a “Four-Wire” Protocol</span>

SPI is commonly referred to as a _four-wire_ protocol because the standard configuration uses four signals:

1. **SCLK** – the clock generated by the master    
2. **MOSI** – master-out, slave-in
3. **MISO** – master-in, slave-out
4. **CS / SS** – chip select (active low)
    
However, this four-wire definition is not always accurate. Depending on the device and communication requirements, SPI can use **fewer** or **more** than four wires.

| Three wires                          | Two wires                            |
| ------------------------------------ | ------------------------------------ |
| ![[Pasted image 20251124082000.png]] | ![[Pasted image 20251124082012.png]] |

If the system only requires communication _from master to slave_, the MISO line is unnecessary.  In that case, SPI reduces to only:

- SCLK
- MOSI

This is common when the slave only receives commands but never sends data back.

Some devices add **auxiliary control pins**. Two common examples are:

- **RESET** – allows the master to reset the slave device hardware.    
- **OE (Output Enable)** – controls when the slave’s output is actually driven to external hardware.
    
The **Output Enable** pin is particularly important in systems like an LED matrix.  
Inside the slave device, the shifted data may be progressively updated bit by bit as it is received. If this internal data were immediately connected to the LEDs, the LEDs would flicker or show random patterns during every shift operation.

To prevent this, the OE pin ensures that:

- while SPI communication is happening, the outputs remain disabled
- **only after the full data frame is received**, the slave enables its outputs and applies the new data to the LEDs
    
This guarantees stable, flicker-free updates. So in practice, your SPI setup might have:

- the standard communication pins
- plus additional control pins such as RESET or OE
- depending on the chip’s requirements
    
This is why SPI is _often_ called a four-wire protocol, but in reality the number of wires varies.

### <span style="color:rgb(161, 40, 226)">Multi-Slave SPI: How Multiple Devices Connect to One Master</span>

SPI allows one master to communicate with several slave devices. There are two main ways to wire this: **independent-slave wiring** and **daisy-chain wiring**.
#### <span style="color:rgb(2, 141, 192)">1. Independent Slave Configuration</span>

![[Pasted image 20251124082647.png|400]]
In the classic SPI setup:
- **MOSI** is shared by all slaves
- **MISO** is shared by all slaves
- **SCLK** is shared
- **Each slave has its own CS (Chip Select)** line

Only the slave whose CS line is pulled **low** becomes active. All other slaves place their MISO line into **high-impedance** so they don’t interfere with communication on the shared data lines.

This prevents collisions—for example, if two slaves tried to drive the MISO line at the same time, you would get corrupted data.

**But there is a drawback:**  
Each slave needs its **own CS pin**, and wiring becomes unmanageable very quickly.  
With 3 slaves, you already need 6–7 wires. With 10 slaves, it becomes a wiring nightmare.
#### <span style="color:rgb(2, 141, 192)">2. Daisy-Chain Configuration</span>

![[Pasted image 20251124082824.png]]

To solve the wiring problem, some systems use a **daisy-chain** layout. Instead of sharing MOSI and MISO across all devices:

- MOSI of the master → MOSI of the _first_ slave
- MISO of the first slave → MOSI of the _second_ slave
- MISO of the second slave → MOSI of the _third_ slave
- …and finally the last slave’s MISO → master’s MISO
    
All devices share the **same CS line**, so they all shift data at the same time.

***Why is this useful?***

Because SPI works like a **shift register**, this setup lets you send a _long chain of bits_ that passes through each device in sequence.

For example, with 8-bit registers:

- To program only the first chip → you still shift 8 bits for each device
- To program the third chip → the data must pass through chip 1 and chip 2 first
    - 8 bits × 3 devices = 24 clock cycles
    
So the chain behaves like one long shift register.

***Advantages***
- Much **fewer wires**
- Only **one chip select** needed
- Cleaner PCB routing
    
***Disadvantages***
- **Slower updates**, because data must pass through all devices in the chain
- You always shift through _every_ device, even if you're only targeting one

## <span style="color:rgb(239, 179, 1)">Clock Polarity and Clock Phase in SPI</span>

Unlike protocols such as **I²C** or **UART**, SPI is **not strictly standardized**. While I²C and UART always behave the same way, SPI can be **configured differently depending on the peripheral**. For this reason, whenever we use SPI, we must carefully match the configuration of the microcontroller with the configuration expected by the sensor or device.

Since SPI communication is **clock-driven**, two key parameters must be defined:

### <span style="color:rgb(161, 40, 226)">1. Clock Polarity (CPOL)</span>

Clock polarity defines the **idle state of the clock signal**.
- If **CPOL = 0**, the clock is idle when **low**
- If **CPOL = 1**, the clock is idle when **high**
    
When communication starts, the clock transitions from its idle state to the active state.  
Depending on the polarity, this transition can be:

- **Low → High**, or
- **High → Low**
    
![[Pasted image 20251215235208.png]]
The correct polarity depends on how the internal logic of the slave device is designed, so it must be programmed accordingly.


### <span style="color:rgb(161, 40, 226)">2. Clock Phase (CPHA)</span>

Clock phase defines **when data is sampled**, relative to the clock transitions.

Inside digital devices, data is stored and transferred using **flip-flops** and **latches**. These elements react either to:

- The **level** of the clock, or
- The **edge** of the clock (rising or falling)
    
![[Pasted image 20251215235243.png|400]]
In SPI, data can be sampled:
- On the **leading edge** of the clock (the first transition after idle), or
- On the **trailing edge** of the clock (the second transition)
    
This choice determines whether data is captured:

- On the **rising edge**, or
- On the **falling edge**
    
Using edge-triggered behavior avoids problems that occur if data changes while the clock remains high or low. By sampling only at clock transitions, data remains stable when it is read.
### <span style="color:rgb(161, 40, 226)">Combining Polarity and Phase</span>

Clock polarity and clock phase work together. This gives **four possible SPI modes**:

- Clock idle **low**, sample on first edge
- Clock idle **low**, sample on second edge
- Clock idle **high**, sample on first edge
- Clock idle **high**, sample on second edge
    
Each SPI device specifies **which mode it requires**, and the microcontroller must be configured to match it exactly. If polarity or phase is wrong, communication will fail even if the wiring is correct.

 ![[Pasted image 20251215235757.png]]
 
All these possibilities lead to **different SPI operating modes**, which depend on the **clock polarity**, the **clock phase**, and therefore on the **idle state of the clock**.

This flexibility is useful because it allows us to adapt the SPI communication to the internal architecture of different devices and to sample data at specific and well-defined moments of the clock signal.

On the other hand, this flexibility is also a **source of confusion**. The master and all the slave devices must be configured **exactly in the same way**. If even one of these parameters (polarity or phase) is different between the master and a slave, the communication will not work correctly and the data will be misinterpreted.

You do not need to memorize all the modes by heart. However, it is important to **look at the timing diagrams** and understand:

- what happens on the **leading edge** and on the **trailing edge** of the clock, and
- **when the data is sampled** in each of the four possible SPI configurations.
    

If you understand these concepts, you will always be able to select the correct SPI mode by simply checking the datasheet of the device you are using.

## <span style="color:rgb(239, 179, 1)">Pros and Cons of the SPI Protocol</span>

One of the main advantages of SPI is that it supports **full-duplex communication**. This means that data can be transmitted and received **simultaneously**, using separate lines for input and output. As a result, SPI communication is very efficient.

Another important advantage is its **high speed**. Unlike protocols that rely on RC charging and discharging effects, SPI uses a dedicated clock signal, which allows much higher data rates. Additionally, SPI is very **flexible**: it is not limited to fixed word sizes such as 8-bit frames. The number of bits transmitted can be chosen depending on the application and the peripheral device.

From a hardware perspective, SPI is often **simple to implement**, especially when only one master and one slave are used.

However, SPI also has several disadvantages. First of all, it requires **many pins**. In addition to the clock and data lines, each slave needs its own chip-select line, unlike I²C, which uses only two shared wires.

Another limitation is that SPI does **not provide an acknowledgment mechanism** from the slave. The master sends data, but it has no direct confirmation that the slave has correctly received it.

In most implementations, SPI also supports **only one master**, which can be a limitation in more complex systems, even though it is not an issue for our application.

SPI is generally suitable only for **short-distance communication**. At high speeds, signal integrity problems may arise due to noise, crosstalk, or propagation delays, especially when multiple devices are involved.

Finally, SPI has **many variations** (different clock polarities, phases, word sizes, and configurations). This makes it less standardized than protocols such as I²C or UART and can complicate development if the master and slave configurations are not perfectly aligned.

![[Pasted image 20251216083745.png]]

Now let’s look at what actually happens on our board. As we said, SPI is used to control the LED matrix, but we need to understand how this is done in hardware. The LED matrix is connected to two relatively large integrated circuits, which are **shift registers**. These shift registers communicate using SPI. More precisely, they are **8-bit serial-in, parallel-out shift registers**. This means that data are sent serially from the microcontroller through SPI and then presented in parallel to drive the LED matrix.

Each shift register has a **serial data input**, which receives the data from the microcontroller, and a **shift clock**. On each rising edge of the shift clock, one bit is shifted into the internal shift register. Therefore, every time the clock goes high, the data move one position inside the register.

However, these devices do not contain only a single shift register stage. Internally, they have two stages. The first stage is the shift register itself, which stores the incoming serial data. The second stage is an **output register**. This second stage is used to ensure that partially transmitted data are not immediately sent to the LEDs. In other words, while the data are still being shifted in, the LED outputs remain unchanged.
![[Pasted image 20251216083807.png|600]]
The transfer from the shift register to the output register is controlled by the **store clock**, labeled **ST_CP**. When the store clock has a rising edge, the data currently stored in the shift register are latched into the output register and then appear on the parallel output pins. In our implementation, this signal is not generated by the SPI peripheral. Instead, it is controlled manually using a GPIO output pin. When this pin goes high, the output data are updated simultaneously.

The chip also includes an **output enable** pin, which provides an additional level of control. This pin allows the parallel outputs to be enabled or disabled entirely. This way, even if the data are already stored, the outputs can be kept inactive until we explicitly allow them.

![[Pasted image 20251216083944.png]]


The shift register provides eight parallel output pins, which are directly connected to the LED matrix. It also has a **serial output**, which allows the data to be forwarded to another shift register. In our case, the two shift registers on the board are connected in a **daisy-chain configuration**. This means that the serial output of the first register is connected to the serial input of the second one.

As a result, both shift registers must be programmed sequentially in order to correctly update the LED matrix. The data are shifted through the first register into the second, and only after all bits have been transmitted do we latch the outputs, ensuring that the entire matrix is updated at the same time..

## <span style="color:rgb(239, 179, 1)">LED Matrix</span>
![[Pasted image 20251216084023.png]]

So far, we have talked a lot about the LED matrix. Now we can actually understand what is happening by looking at the schematic.

On the schematic, we can see the SPI interface coming from the microcontroller. There are also some LEDs that can be used as indicators, for example to check whether the communication is working correctly. Most importantly, we can see the two shift registers, which are connected in **daisy-chain mode**, as discussed before.

One of these shift registers controls the **rows** of the LED matrix, while the other one controls the **columns**. In this way, using only two shift registers, we can control the entire LED matrix, which is relatively large: it has **five columns and seven rows**. This allows us to display many different patterns, such as characters, symbols, or simple drawings.

To understand how a single LED is turned on, let’s look at how the matrix is connected. Each LED is connected between a row line and a column line. When a bit corresponding to a row is set to 1, that entire row is enabled. Similarly, when a bit corresponding to a column is set to 1, that column is activated (in this case, typically pulled to ground). An LED lights up only when both its row and its column are enabled at the same time.

However, this creates a problem. Suppose we want to turn on two LEDs: one in the first row and first column, and another one in the third row and second column. If we simply enable the first and third rows, and at the same time enable the first and second columns, we do not get only those two LEDs. Instead, all the LEDs at the intersections of the selected rows and columns will turn on. This means that we will also unintentionally light up additional LEDs.

To avoid this issue, we use a technique called **multiplexing**. Instead of enabling multiple columns at the same time, we activate **one column at a time**. For each column, we enable only the rows corresponding to the LEDs that should be on in that column. Then we disable the column and move on to the next one.

In practice, the process works as follows: we enable the first column and set the row bits according to the LEDs we want to turn on in that column. Then we disable the first column, enable the second column and set its corresponding rows, then move on to the third, fourth, and fifth columns, and finally repeat the cycle.

If this switching is done fast enough, the human eye does not perceive the columns turning on and off individually. Instead, due to persistence of vision, the LEDs appear to be steadily lit, and the intended character or pattern becomes visible on the matrix.

In summary, the rows determine **which LEDs are on within a column**, and the columns are **scanned one at a time** using multiplexing to avoid unwanted LED activation.

![[Pasted image 20251216085107.png]]
Here are a few additional descriptions to complete the picture. I assume that all of you are already familiar with how LEDs work in combination with resistors, so I will not go into that part in detail.

Once again, the LEDs are controlled by selecting a **specific combination of rows and columns**. An LED turns on only when its corresponding row and column are both enabled.
![[Pasted image 20251216085131.png]]
Now, let’s focus on how the data are transferred to the LED matrix. Since the two shift registers are connected in **daisy-chain mode**, we need to send **16 clock pulses** instead of just 8. This is because we must program both shift registers: one for the columns and one for the rows. In other words, we send 8 bits for one register and another 8 bits for the second register, all in a single SPI transmission.

The data are written **one column at a time**. After the data have been shifted into the registers, the latch (or store clock) is activated so that the new values are transferred to the outputs. At this point, the selected column is enabled, and the corresponding rows determine which LEDs in that column are turned on.

![[Pasted image 20251216085201.png]]

It is important to note that only **one column can be active at any given time**. This is necessary to avoid unintended LED activation, as explained before. To display a full image or character, the system rapidly cycles through all columns, updating the row data for each one in turn.

To ensure that the image appears stable to the human eye, the **refresh rate must be higher than about 50 Hz**. In practical terms, this means that each column should be active for less than roughly 4 milliseconds. If this condition is met, the human eye will not perceive the LEDs turning on and off, but instead will see a steady, continuous image.

In that file, you can draw the desired pattern by marking the LEDs (for example, with an “X”) in the matrix. The file will then automatically generate the corresponding bit patterns for the columns and rows. This makes it much easier to program the two shift registers correctly and light up exactly the LEDs you want.

### <span style="color:rgb(161, 40, 226)">Handling multiple timers</span>

Since we are using **two timers**, both of them will trigger the same callback function. For this reason, inside the callback we must always **check which timer caused the interrupt**.

- **Timer 3 is used to scan the LED matrix columns.

For Timer 2, a simple and effective approach is to use a **flag or index variable**, initialized to zero.

Each time Timer 2 triggers:

- a new letter pattern is copied from a “storage” matrix (for example, letter A, B, or C),
- into a **working matrix** that is always read by the column-scanning code.

This way, the scanning code always accesses the same variable, which simplifies the logic.

The index is then incremented and wrapped around (for example from 0 to 2 if you have three letters). This creates a simple cycle of characters.   

Timer 3: scanning the columns

Timer 3 is responsible for **displaying the LED matrix**.

Each time it triggers:
- two bytes are transmitted via **SPI in DMA mode**,
- one byte programs the **rows**,
- the other byte programs the **columns**  
    (the order depends on how the shift registers are connected; in this case rows are sent first, then columns).
~~~~c#
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim){
	
	if(htim==&htim2){
		if(flag==0){
			memcpy(matrix, matrix_A,sizeof(matrix));
			flag=1;
		}
		else{
			memcpy(matrix, matrix_6, sizeof(matrix));
			flag=0;
		}
	}
	if(htim==&htim3){
		HAL_SPI_Transmit_DMA(&hspi1, matrix[column_index],2);
	}
}
~~~~



Because SPI is used in **DMA mode**, once the transmission is complete, the **SPI transmit complete callback** is automatically called.


### <span style="color:rgb(161, 40, 226)">SPI callback: updating the LED matrix</span>

Inside the SPI DMA callback:

~~~~c#
void HAL_SPI_TxCpltCallback(SPI_HandleTypeDef *hspi){
	HAL_GPIO_WritePin(RCLK_PIN, GPIO_PIN_SET);
	column_index++;
	if(column_index==5){
		column_index=0;
	}
	HAL_GPIO_WritePin(RCLK_PIN, GPIO_PIN_RESET);
}
~~~~
1. The **RCLK pin is set high**, enabling the output of the shift registers.
2. This briefly displays the LEDs for the current column.
3. The **column index is incremented** so that the next column will be displayed on the next timer event.
4. The RCLK pin is then **reset**, disabling the output again.
    
This short “flash” is more than enough for the human eye. Because this process happens very fast, our eyes perceive the image as **stable**, not blinking.

Disabling the output after each update is important. While new data is being shifted in, we do **not** want the LEDs to reflect intermediate values.

The column index cycles from 0 to 4 (for a 5-column matrix) and then wraps back to 0.
